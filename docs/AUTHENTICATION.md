# Authentication

Sign-in posts credentials to the backend, keeps the short-lived access token in the in-memory `SessionStore`, and stores only the rotating refresh credential in browser `sessionStorage`. At startup the app refreshes that credential and loads the current user before protected routes render, so a full refresh or direct protected URL in the same tab restores the session. Browser-tab closure may end the session. `localStorage` is never used.

After an API 401, one coordinated refresh is shared by simultaneous requests. The original request is retried at most once. Failed refresh or authentication clears in-memory and `sessionStorage` state and routes to `/account/login` with a validated root-relative return path. External URLs, protocol-relative URLs, backslashes and control characters are rejected. Logout invalidates the backend refresh sessions and clears browser state; password change clears the session because the backend invalidates its security stamp. Login credentials and tokens never appear in URLs, rendered markup, logs or error messages. Backend authorization remains authoritative; client roles only tailor navigation.

The session-storage choice is an intentional school-project tradeoff for separately hosted frontend/backend domains; same-origin scripts can read it. For production, prefer a backend-for-frontend with secure HttpOnly cookies and a separately designed CSRF contract. The frontend host must send a restrictive CSP; allow `connect-src` only to the deployed API origin and same-origin app assets.

Password recovery/reset delivery is intentionally unavailable. The UI says: “Password recovery is currently unavailable. Contact your facility administrator.” There are no reset links or reset-token controls. Staff credentials are supplied through a masked form during creation and are not shown after submission; delivery is not claimed.
